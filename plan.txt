# Autonomous Agent System Productization Plan

## Goal

Turn this repository from an agent-agnostic prompt pack into a working autonomous delivery system that:

- pulls work from GitHub Issues
- pulls work from `todo.json` when local or offline execution is preferred
- orchestrates a team of agents through a deterministic pipeline
- verifies changes before reporting success
- learns from repeated successful workflows
- integrates cleanly with the existing agent-memory database and MCP tooling
- converges cleanly with the existing Anvil execution platform instead of duplicating its runtime surfaces

## Planning Principles

- productize the runtime without re-coupling the prompts to a single host
- keep this repository as the canonical workflow/spec layer while converging runtime execution into Anvil where practical
- support both GitHub Issues and `todo.json` as first-class task systems
- treat agent-memory validation as a gated dependency because major infrastructure changes already occurred
- make self-improvement measurable, not aspirational
- promote proven workflows into scripts and skills instead of storing everything as loose memory
- keep the runtime cross-operating-system compatible, which means shell can remain a thin export layer but not the core orchestrator
- stay DRY across API, MCP, CLI, and agent tool layers by reusing shared Python service modules rather than reimplementing logic per interface
- target production-grade behavior: resumability, typed contracts, deterministic routing, bounded authority, observable artifacts, and graceful degradation

## Track 2: Runtime Core

### 2.1 Choose implementation language

- Use Python or TypeScript for the runtime core. Do not use shell as the primary orchestration layer.
- Decision gate:
  - prefer Python if the strongest requirement is reliability, schema validation, and tight integration with the existing Python-based agent-memory service
  - prefer TypeScript if the strongest requirement is a single JavaScript runtime across Bun, Node, and future host tooling
  - Bun is acceptable as a package runner or execution target for a TypeScript runtime, but the code should remain standards-based so Node compatibility is preserved
  - keep shell only for tiny wrappers such as export, bootstrap, or convenience commands

### 2.2 Build orchestrator skeleton

- Add either `scripts/run_pipeline.py` or `src/run_pipeline.ts`.
- Phases:
  - INIT
  - PICK
  - PLAN
  - DEV
  - TEST
  - REVIEW
  - PR
  - REPORT
  - IMPROVE
- Add resumable local state in `.autonomous-state.json`.

### 2.2B Converge runtime ownership with Anvil

- Treat this repository as the canonical workflow/prompt/spec layer.
- Treat Anvil as the primary execution platform for:
  - coding-agent runtime
  - FastAPI service surface
  - MCP exposure
  - local tool execution
  - worker loop and persistent task execution
- Keep this repository’s runtime as a reference implementation and compatibility harness until Anvil reaches parity.
- Done when the production path is clear:
  - prompts and contracts live here
  - execution and service integration live in Anvil
  - both systems share schemas and task semantics instead of drifting apart

### 2.3 Add typed schemas

- Config schema for `.autonomous.json`
- Canonical task schema
- Subtask schema
- Agent result schema
- Run-state schema
- Artifact manifest schema

### 2.4 Add artifact capture

- Persist per-run outputs under `artifacts/<run-id>/`
- Capture:
  - command transcripts
  - test output
  - review findings
  - diff stats
  - generated plans
  - promotion candidates

## Track 5: Agent Team Execution Model

### 5.1 Define agent contracts in code

- For each specialist, capture:
  - required inputs
  - optional inputs
  - read-only or writable status
  - allowed write scope
  - expected output schema
  - escalation conditions

### 5.2 Implement bounded parallelism

- Allow only non-overlapping write scopes in parallel.
- Use read-only agents freely for planning, review, and diagnostics.
- Gate each parallel layer behind a merge and verification step.

### 5.3 Add branch and merge strategy

- One task branch per parent task
- Optional temporary worker branches or worktrees for subtasks
- Merge back after each verified layer
- One final PR

## Track 5B: Shared Platform And DRY Service Boundaries

### 5B.1 Inventory shared runtime surfaces

- Audit the Anvil codebase and classify current capabilities into:
  - shared service layer
  - FastAPI endpoints
  - MCP tools
  - CLI commands
  - in-agent tool registry
- Explicitly identify where the same concept is exposed more than once.
- Done when every new capability has a single implementation owner and thin adapters for each interface.

### 5B.2 Define the production-grade layering model

- `core services`
  - reusable Python modules with typed inputs/outputs
  - no UI or transport assumptions
- `transport adapters`
  - FastAPI
  - MCP
  - CLI
  - agent tool registry
- `workflow/spec layer`
  - prompt pack in this repository
  - contracts for phases, specialists, and handoffs
- `memory layer`
  - agent-memory for durable lessons, patterns, and benchmarks
- Done when each feature can be added once and surfaced everywhere.

### 5B.3 Move duplicate logic behind shared services

- Web retrieval, local search, planning/todos, and task normalization should each have one implementation path.
- FastAPI handlers should call shared service modules.
- MCP handlers should call the same shared service modules.
- CLI commands and slash commands should call the same shared service modules.
- Agent tools should call the same shared service modules.
- Done when no feature requires separate business logic for API, MCP, CLI, and tool mode.

## Track 6B: Planning And Retrieval Harness

### 6B.1 Add first-class planning

- Add a persistent plan/todo model with typed items:
  - id
  - title
  - status
  - owner
  - dependencies
  - notes
  - acceptance criteria
- Provide one planning implementation and expose it through:
  - FastAPI

  - `write_todos`
  - `/plan`
  - `/todo add`
  - `/todo done`
  - `/todo block`
- Done when planning survives across iterations and can be inspected or updated outside the LLM loop.

### 6B.2 Add cohesive retrieval model

- Local retrieval:
  - explore workspace tree
  - search file names
  - search file contents
  - search memory
- Internet retrieval:
  - search web
  - fetch URL content
  - cache/fingerprint fetched results when appropriate
- Prefer shared service modules over ad hoc tool-only code.
- Done when Anvil exposes a coherent retrieval surface across agent, CLI, FastAPI, and MCP.

### 6B.3 Enforce retrieval and planning policy

- Search local first for repo-scoped implementation questions.
- Use memory search before repeating known workflows.
- Use internet search only when local sources are insufficient or freshness matters.
- Record web-sourced artifacts separately from local run artifacts.
- Do not let web retrieval bypass security, provenance, or artifact capture rules.

## Track 7: Continuous Improvement Engine

### 7.1 Mine repeated workflows

- Parse command transcripts and run artifacts.
- Detect repeated successful command sequences.
- Detect repeated retries caused by missing preflight checks or fragile command syntax.

### 7.2 Promotion rubric

- Promote to memory when the pattern is durable but low-frequency.
- Promote to playbook when the sequence needs structured human-readable steps.
- Promote to script when the sequence is deterministic and repeated.
- Promote to prompt-pack changes when the improvement is judgment-oriented.

### 7.3 Define benchmarks

- number of commands per completed task
- manual interventions per task
- median time per phase
- verification pass rate on first attempt
- reopened or blocked tasks
- number of promoted workflows

### 7.4 Add explicit self-improvement backlog

- each promotion candidate becomes:
  - direct implementation if cheap and safe
  - otherwise a GitHub Issue tagged `autonomous:follow-up`

This is the operational loop that lets the system improve its own productivity instead of just “remembering more.”
